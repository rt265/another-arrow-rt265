# 变更记录 23：棋盘尺寸上限的实测与说明

本轮不改玩法、不改界面，只回答一个问题并把它钉进文档：**当前生成器最大支持多大的棋盘？**
结论写进了 `generator.py` 的两处 docstring（`LevelSpec` 与 `generate_level`），
实测数据记录如下。

## 1. 代码里没有硬上限

`LevelSpec.__post_init__` 只校验“尺寸为正、箭头数不超过格子数”：

```python
if self.rows < 1 or self.cols < 1:
    ...  # 尺寸无上限
if not 1 <= self.arrows <= self.rows * self.cols:
    ...
```

所以“最大尺寸”不是常量，而是**逆向构造的成功率**与**屏幕格子大小**两条软约束共同决定的。

## 2. 生成侧：能摆下的箭头密度随尺寸单调下降

`generate_level` 逐支摆放，每支都要求它的前进方向上还没有箭头；棋盘越大，射线上
的格子越多，“整条射线恰好为空”的概率越低，于是**可摆下的密度上限跟着尺寸一起降**。
用 `generate_solvable_level`（200 次重试）逐个尺寸扫描“最大箭头数”，实测：

| 棋盘 | 最大箭头数 | 密度 | 棋盘 | 最大箭头数 | 密度 |
|--|--|--|--|--|--|
| 6x6 | 34 | 0.944 | 16x16 | 154 | 0.602 |
| 8x8 | 55 | 0.859 | 18x18 | 177 | 0.546 |
| 10x10 | 78 | 0.780 | 20x20 | 208 | 0.520 |
| 12x12 | 101 | 0.701 | 22x22 | 231 | 0.477 |
| 14x14 | 127 | 0.648 | 24x24 | 271 | 0.470 |

三点值得记住：

- **“密度 >3/4 就很难”是旧说法，只对小棋盘成立**：6x6 能塞到 0.94，而 12x12 在
  0.75 就已经失败。手写 docstring 时按尺寸描述才对；
- 失败会**烧满 200 次重试**才抛 `GenerationError`：尺寸越大重试越贵（20x20 之后
  单次尝试就要毫秒级，整轮失败可到 1 秒以上），所以别把关卡生成放到每帧路径上；
- 本轮的扫描只做到 **24x24**：24x24 在 0.47 密度下仍稳定成功，再大就不在支持范围内。

## 3. 显示侧：格子会先于生成变得不可用

`Board._layout` 取 `cell_size = min(area.width // cols, area.height // rows, MAX_CELL_SIZE)`
（`board.py`）。默认 720×720 窗口下 `ui.board_area()` 实测是 `Rect(32, 128, 656, 552)`，于是：

- 6x6 → 格子 92px（圆片半径 32.0px，正常观感）；
- 24x24 → 格子 23px（扣掉 `CELL_GAP` 后内边宽 11px，圆片半径 4.4px）。

也就是说 24x24 时箭头只有几个像素，**“能生成”不等于“能玩”**。

## 4. 显示侧方棋盘实测：能撑到多大

脚本 `.preview/board_size_display.py`（临时脚本）在**默认 720×720 窗口**下逐个尺寸渲染方棋盘，
关卡用合成数据（棋盘格铺 50% 密度、四个方向轮换），避免把生成器的密度限制混进显示侧的结论：

| 棋盘 | 格子 | 内边宽 | 圆片半径 | 图形外延 | 观感 |
|--|--|--|--|--|--|
| 6x6 | 92px | 80px | 32.0px | 28.2px | 宽敞 |
| 8x8 | 69px | 57px | 22.8px | 20.1px | 舒服 |
| 10x10 | 55px | 43px | 17.2px | 15.1px | 舒服 |
| 12x12 | 46px | 34px | 13.6px | 12.0px | 舒服 |
| 14x14 | 39px | 27px | 10.8px | 9.5px | 舒服（舒适区下沿）|
| 16x16 | 34px | 22px | 8.8px | 7.7px | 可读，笔画略毛糙 |
| 18x18 | 30px | 18px | 7.2px | 6.3px | 可读，笔画开始发糊 |
| 20x20 | 27px | 15px | 6.0px | 5.3px | 勉强，箭头已经像小色块 |
| 24x24 | 23px | 11px | 4.4px | 3.9px | 不可用，四个方向分不出来 |

口径：内边宽 = 格子 − 2×`CELL_GAP`(6)；圆片半径 = `Board.chip_radius()` = 内边宽 ×
`ARROW_CHIP_RATIO`(0.40)；图形外延 = 圆片半径 × `ARROW_GLYPH_RATIO`(0.88)。
另用“中心格里图形原色的像素数”当客观旁证：6x6 是 1030 个，16x16 78 个，
20x20 31 个，24x24 只剩 8 个（已经画不成笔画）。

**结论：默认窗口下，方棋盘的舒适上限是 14x14~16x16**；18x18 起要靠猜，20x20 以上
四方向不可分。布局本身不设限（棋盘总能居中缩放，右下角的辅助线开关也没被压到），
**瓶颈纯粹是每个格子的像素数**。

窗口放大能直接抬高上限（棋盘跟着视口等比放大，`MAX_CELL_SIZE` 也一起放大）：

| 窗口 | 缩放 | 16x16 | 18x18 | 20x20 | 24x24 | 32x32 |
|--|--|--|--|--|--|--|
| 720x720 | 1.000 | 34px | 30px | 27px | 23px | 17px |
| 900x900 | 1.250 | 43px | 38px | 34px | 28px | 21px |
| 1080x1080 | 1.500 | 51px | 46px | 41px | 34px | 25px |
| 1440x1440 | 2.000 | 69px | 61px | 55px | 46px | 34px |

想玩 20x20 以上，至少要 1080×1080；非方（矩形）棋盘按同一口径算：可用区域是
656×552，想保住 34px 的格子就是 16 行 × 19 列。

## 5. 落地的改动

只有 docstring（无行为改动）：

- `LevelSpec`：写明 `rows` / `cols` 没有硬上限，但**建议不超过 16x16**（默认窗口下
  16x16 的格子只剩 34px），生成侧也只验证到 24x24；
- `generate_level`：`Returns` 段落把“密度 >3/4 变难”改写成**按尺寸给出实测数字**
  （6x6 0.94 → 24x24 0.47，见第 2 节）；新增 `Note` 段落，按第 4 节的显示侧实测给出
  结论——**显示侧比生成侧先失效**，所以“建议棋盘不超过 16x16”，更大的不保证可用
  （棋盘虽然跟着窗口等比放大，但得把窗口一起放大才顶得住：1080×1080 下 24x24 的
  格子才回到 34px）。

顺带核对了 24x24 / 271 支的关卡能真的装进 `Board`（`Board(level, ui.board_area())`
不报错，`cell_size == 23`）。

## 6. 校验

本轮**没有动任何源码**：显示侧的测量全部在 `.preview/board_size_display.py`（临时脚本，
已被 .gitignore 忽略）里跑，产物是 `board-size-{6,8,10,12,14,16,18,20,24}.png`、
`board-size-sheet.png`（总览）与 `board-size-zoom.png`（每格约 100px 的放大对照表）。
上半轮（生成侧）只在 `generator.py` 的两处 docstring 上动过，无行为改动。

`uv run ruff check .`、`uv run ruff format --check`、`uv run ty check` 全部通过。
`uv run pytest -q` 的结果是 **474 passed / 3 failed**，3 条失败与本轮无关：
工作区里 `ui.py` 正在被改动（`settings_page` 去掉了 `sections` 与 `hint`），
`tests/test_ui.py` 与 `tests/test_game.py` 中依赖这两块的 3 条测试因此报
`IndexError` / `AssertionError`。
